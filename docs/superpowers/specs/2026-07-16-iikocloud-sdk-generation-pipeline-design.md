# Конвейер генерации и проверки Iikocloud Python SDK

Дата: 2026-07-16
Статус: утверждённый дизайн, ожидающий реализации

## 1. Результат

Репозиторий должен воспроизводимо превращать официальную OpenAPI-схему iiko Cloud в устанавливаемую Python-библиотеку. Некорректности upstream-схемы исправляются отдельно от исходного файла, результат проверяется offline-тестами и осторожными live-тестами, а публикация в Git не может случайно включить секреты или частные HTTP-данные.

Готовый SDK будет устанавливаться в `Iikocloud-manager` как обычная зависимость из зафиксированного Git tag. Архитектуру manager предполагается впоследствии приблизить к схеме `Iikoserver-manager` + `Pub-iikoserver-py-sdk`, но это отдельный проект. Настоящий дизайн охватывает только SDK и его конвейер.

## 2. Контекст и обнаруженные проблемы

На момент проектирования официальная схема доступна через ReDoc по адресу `https://api-ru.iiko.services/docs`, а JSON-схема — по адресу `https://api-ru.iiko.services/api-docs/docs`.

Проверенный upstream snapshot содержит:

- OpenAPI 3.0.1;
- 224 пути и 225 операций;
- 721 схему;
- отсутствие `operationId` у всех операций;
- 59 употреблений невалидных или нестандартных типов;
- сотни неудобных CLR/generic-имён схем;
- некорректный `required` как минимум у `ExternalMenuComboItem`;
- 12 конструкций `oneOf`, включая ответ `/api/2/menu/by_id` и элементы внешнего меню;
- неоднозначные композиции моделей меню, которые нельзя безопасно исправлять удалением веток.

Текущий локальный snapshot заметно отстаёт от upstream. Существующий `codegen.sh` ссылается на удалённый `prepare_openapi.sh`, использует `--skip-validate-spec` и незакреплённый образ генератора. Сгенерированные тесты являются пустыми заглушками, а часть generated-кода изменялась вручную. Поэтому текущий процесс не является ни воспроизводимым, ни проверяемым.

## 3. Цели

1. Хранить точный upstream snapshot без ручных изменений.
2. Хранить все исправления схемы как обозримый и проверяемый correction layer.
3. Получать одинаковый SDK из одинаковых входных данных и закреплённого toolchain.
4. Останавливать генерацию при изменении upstream-контекста, на который опирался патч.
5. Поддерживать корректные `oneOf` и другие композиции, не теряя варианты ответа.
6. Иметь полезные offline, live-read и opt-in live-write тесты.
7. Никогда не повторять запрос после `429` и не переключать учётные данные автоматически.
8. Уметь сохранять только очищенные HTTP-примеры в приватном, игнорируемом каталоге.
9. Собирать wheel и устанавливать SDK из Git tag в другой проект.
10. Делать commit/push отдельным явным действием после всех обязательных проверок.

## 4. Не входит в первую итерацию

- рефакторинг `Iikocloud-manager`;
- совместимость с публичными именами текущего сгенерированного SDK;
- автоматическое исправление неизвестных семантических ошибок upstream;
- автоматический запуск live-тестов из CI;
- автоматический перебор или ротация API login;
- публикация в PyPI;
- выполнение необратимых write-операций;
- собственные Mustache-шаблоны без доказанного дефекта генератора.

## 5. Основные архитектурные решения

### 5.1 Overlay-first вместо ручной правки

Официальный snapshot неизменяем. Все исправления применяются при построении effective schema. Ручная правка upstream JSON и сгенерированных Python-файлов запрещена.

### 5.2 Generated-код отделён от рукописного

Генератор владеет API-классами, моделями и связанной документацией. Упаковка, transport adapters, pipeline, safety-механизмы и тестовая инфраструктура остаются рукописными. Это позволяет полностью заменить generated-область без потери инфраструктуры.

### 5.3 Низкоуровневый SDK не управляет политикой нагрузки

SDK предоставляет вызовы API и штатную конфигурацию авторизации, но не добавляет скрытые retries и автоматический throttling. Канонические сведения о лимитах поставляются как метаданные и используются live-тестами; будущий manager сможет использовать те же данные для собственной политики.

### 5.4 Live-доступ считается опасной операцией

У тестового API login могут быть все права. Поэтому безопасность обеспечивается не названием «read-only», а разделением тестов, явными флагами, allowlist окружений, последовательным запуском, бюджетами запросов и журналом мутаций.

## 7. Поток данных

```text
официальный JSON
  -> точный upstream snapshot
  -> inventory и guarded correction layer
  -> effective OpenAPI
  -> lint + official validation
  -> генерация во staging
  -> package/unit/contract tests
  -> manifest-controlled promotion
  -> необязательный live smoke
  -> явная публикация
```

Промежуточные файлы создаются только в `build/`. Рабочая generated-область обновляется после полного успеха предыдущих стадий. Ошибка не должна оставлять наполовину обновлённый SDK.

## 8. Получение upstream-схемы

Команда:

```bash
uv run python -m tools.openapi_pipeline sync
```

должна:

1. Скачать схему по закреплённому URL с конечным timeout.
2. Проверить, что ответ является JSON и содержит ожидаемую OpenAPI-структуру.
3. Рассчитать SHA-256 исходного тела.
4. Сохранить точные байты как candidate snapshot в `build/upstream/`, без форматных и семантических исправлений.
5. Построить inventory и diff относительно committed snapshot.
6. Продолжить коррекцию и генерацию только после успешной проверки формата.

Если hash не изменился, `sync` завершается без изменения generated-кода. Сетевые ошибки не приводят к использованию неизвестного частичного ответа. Повторный запуск с уже committed snapshot возможен отдельным offline-режимом, но не маскирует неудавшееся обновление.

Candidate snapshot, effective schema и generated-код продвигаются в рабочее дерево как одна логическая транзакция после всех offline gates. При stale overlay или ошибке генерации candidate остаётся в игнорируемом `build/` для диагностики, а committed snapshot и SDK не расходятся.

## 9. Correction layer

### 9.1 Типы исправлений

Механические исправления покрывают известные однозначные нормализации:

- `bool` -> `boolean`;
- `int` -> `integer`;
- `uuid` -> `string` + `format: uuid`;
- псевдотипы массивов -> `type: array` + `items`;
- поддерживаемые записи `integer <int32/int64>` и `string <uuid>`;
- заранее описанные операции нормализации CLR/generic-имён.

Семантические исправления покрывают конкретные контракты:

- неправильный `required`;
- отсутствующие или ошибочные properties;
- `nullable`, `oneOf`, `allOf` и discriminator;
- неверные enum/default;
- расхождение request/response с подтверждённым поведением сервера.

### 9.2 Guarded overlays

Исправления схемы хранятся в OpenAPI Overlay YAML. Детерминированный applier поддерживает служебные `x-iiko-sdk-*` поля с:

- идентификатором upstream-проблемы;
- ожидаемым старым значением или hash фрагмента;
- ожидаемым числом совпадений JSONPath;
- обоснованием;
- ссылкой на минимизированный fixture или публичную документацию.

Ни одно действие не может примениться к нулю или неожиданному числу узлов. Несовпадение guard означает stale overlay и останавливает `sync`. Новый невалидный тип, не покрытый известным правилом, обнаруживается последующей валидацией и также останавливает процесс.

Секретные capture-файлы не являются переносимым доказательством. Подтверждённый контракт переносится в минимизированный синтетический fixture после ручного просмотра; fixture сохраняет форму, типы и значимые enum, но не реальные идентификаторы и пользовательские строки.

### 9.3 Реестр operationId

Все публичные имена операций закрепляются в `openapi/operation-ids.yaml`. Первичные кандидаты можно получить из HTTP-метода, пути и тега, но они проходят просмотр перед включением.

Инварианты:

- каждая операция имеет один уникальный `operationId`;
- один `operationId` не переезжает между операциями молча;
- новая upstream-операция блокирует генерацию до добавления имени;
- генератор не придумывает публичные имена самостоятельно.

После первого чистого выпуска registry становится частью публичного контракта библиотеки.

### 9.4 Имена моделей

Normalizer удаляет только известный технический CLR-шум и сохраняет доменный смысл. Явные исключения находятся в `model-name-overrides.yaml`.

Если разные upstream-схемы получают одно Python-имя, pipeline завершается ошибкой. Числовые суффиксы для молчаливого разрешения коллизий запрещены. Inline schemas получают явный title или закреплённое mapping-имя.

## 10. Полиморфизм и `oneOf`

Ветки `oneOf` нельзя удалять только ради успешной генерации. Для каждого проблемного места применяется следующая лестница:

1. Исправить невалидный upstream-контракт overlay-патчем.
2. Сделать варианты взаимоисключающими с помощью подтверждённых enum/const/discriminator.
3. Использовать штатные mappings OpenAPI Generator.
4. Если OpenAPI валиден, но генератор имеет локальный дефект, заменить одну модель через `importMapping` на изолированную рукописную реализацию.
5. Изменить минимальный Mustache-шаблон только после воспроизводящего теста и фиксации версии генератора.

Известные места для первичной реализации:

- для ответа `/api/2/menu/by_id` проверить фактические значения `formatVersion` у `ExternalMenuV2/V3/V4`, затем сделать варианты однозначными;
- для `ExternalMenuComboItem` восстановить настоящий набор properties/required по очищенному live-примеру вместо удаления combo-ветки;
- для dish/combo discriminator не предполагать значение поля без фактического доказательства;
- nullable-обёртки с одной ссылкой привести к форме, корректной для OpenAPI 3.0 и выбранного генератора.

До получения доказательства спорная семантическая коррекция должна оставаться заблокированной, а не угадываться.

## 11. Генерация SDK

Версия OpenAPI Generator должна быть точной, стабильной и не snapshot. Версия и digest Docker-образа хранятся в `generator/toolchain.lock`; их изменение является отдельным обозримым обновлением.

Запрещено:

- использовать `latest`;
- использовать `--skip-validate-spec`;
- генерировать непосредственно поверх рабочего дерева;
- исправлять generated Python вручную.

Генерация происходит в `build/generated/`. Затем выполняются:

1. импорт всех сгенерированных модулей;
2. тесты сериализации и десериализации;
3. contract-тесты композиционных моделей;
4. сборка wheel;
5. установка wheel в чистое окружение;
6. smoke import установленного пакета.

Только после успеха manifest-controlled promotion заменяет файлы, которыми владеет генератор, и удаляет устаревшие generated-файлы. Корневой `pyproject.toml`, pipeline и инфраструктура тестов не перезаписываются генератором.

## 12. Валидация и отчёт об изменениях

Effective schema обязана пройти:

- разрешение всех `$ref`;
- проверку допустимых OpenAPI 3.0 типов и formats;
- `required` как подмножество properties;
- уникальность `operationId`;
- отсутствие коллизий публичных имён моделей;
- проверку array `items`;
- sanity-проверки `oneOf`/`allOf`/discriminator;
- проверку servers и схем авторизации;
- штатную validation-команду OpenAPI Generator.

Каждый `sync` пишет игнорируемые отчёты:

```text
build/reports/upstream-diff.md
build/reports/upstream-diff.json
```

Отчёт содержит добавленные, удалённые и изменённые операции/схемы, состояние overlays, изменения публичных имён и новые composition-конструкции.

Команда:

```bash
uv run python -m tools.openapi_pipeline verify
```

работает offline, регенерирует SDK во временный каталог и требует нулевой разницы с committed generated-кодом.

## 13. Стратегия тестирования

### 13.1 Обычный `pytest`

Запуск без специальных флагов выполняет только offline-тесты:

- unit-тесты pipeline;
- тесты applier и stale guards;
- тесты naming registries;
- schema lint;
- generated import/serialization tests;
- contract tests на синтетических fixtures;
- package build/install smoke.

Сгенерированные заглушки с `pass` не считаются тестовым покрытием и не используются как gate.

### 13.2 Live read

Live read разделён на два маркера:

```bash
uv run pytest -m live_read_smoke -n0 --live-profile test-server
uv run pytest -m live_read_full -n0 --live-profile test-server
```

`smoke` выполняет минимальный набор canary-вызовов после значимого изменения. `full` запускается редко и вручную. Оба режима строго последовательны.

Успешный запуск создаёт игнорируемую receipt с environment fingerprint, списком операций и hash effective schema/generated-кода. Receipt действительна только для точного сочетания этих hash и профиля; изменение любого из них или получение `429` аннулирует её. Искусственный временной срок не заставляет повторять те же запросы без изменения кандидата.

### 13.3 Live write

Write-тесты находятся в `tests/integration/write/`, но не входят в обычный `pytest`, `verify` или CI. Запуск требует одновременно:

```bash
uv run pytest -m live_write -n0 \
  --allow-live-write \
  --live-profile test-server \
  --target-organization UUID
```

- CLI-флаг `--allow-live-write`;
- `allow_write = true` в локальном профиле;
- точное совпадение UUID с allowlist;
- выделенный тестовый API login;
- отсутствие параллельного запуска;
- наличие rate-limit plan;
- предварительный вывод mutation plan.

Операции делятся на:

1. reversible — разрешены при наличии проверенного cleanup;
2. compensating/audit residue — требуют `--allow-audit-residue`;
3. irreversible — отключены.

Типичный тест выполняет `create -> verify -> update -> verify -> cleanup`. Cleanup регистрируется сразу после успешного create, до первого assertion.

До первой мутации runner резервирует rate-limit budget для всех обязательных cleanup-вызовов. Если резерв невозможен, тест не начинает мутацию. Зарезервированный budget нельзя расходовать на assertions или необязательные шаги.

## 14. Защита от rate limit

Каноническая конфигурация хранится в `contracts/rate-limits.yaml`. Для операции отдельно задаются документированный/наблюдаемый server limit и более строгий test budget.

Начальные безопасные правила:

- не более одного вызова одной операции за один test run;
- глобальный интервал между live-запросами не менее 15 секунд;
- test budget использует не более 20% известного server limit;
- для лимита `1 запрос за N секунд` минимальный интервал равен `5 * N`;
- неизвестная операция запрещена до явного добавления лимита;
- параллельный live-запуск запрещён;
- один API login используется только одной активной сессией.

Получение access token также является операцией с отдельным бюджетом. За одну live-сессию token запрашивается не более одного раза и хранится только в памяти.

Состояние хранится в `.state/live-rate-limits.json`, раздельно по environment fingerprint и `operationId`. Fingerprint не содержит token или API login.

Если тот же API login используется на другой машине или другим приложением, локальный state не способен обеспечить общий лимит. Поэтому live-запуск требует эксклюзивного окна либо отдельной учётной записи.

При любом `429`:

1. весь suite останавливается;
2. retry запрещён;
3. автоматическая смена API login запрещена;
4. профиль переводится в circuit-open;
5. reset выполняется только вручную после проверки реального окна лимита.

## 15. Журнал мутаций и cleanup

Каждый write-run создаёт `.state/mutations/<run-id>.json`. После создания ресурса идентификатор и cleanup action записываются атомарно до выполнения дальнейших assertions.

Cleanup stack выполняется LIFO в `finally`. Ошибка cleanup делает весь запуск неуспешным и сохраняет журнал. Команда `cleanup-orphans` повторяет только заранее зарегистрированные безопасные действия и также подчиняется rate-limit policy.

Все тестовые сущности получают уникальный префикс `sdk-test-<run-id>`. Это облегчает ручной поиск, но не заменяет журнал.

`finally` не гарантирует откат после `kill -9`, падения машины или операции с аудитным следом. Persistent journal является обязательным вторым уровнем защиты.

## 16. Безопасный HTTP capture

Capture включается только явно:

```bash
uv run pytest -m live_read_smoke -n0 \
  --live-profile test-server \
  --capture-http \
  --capture-operation get_external_menu_by_id
```

Файлы сохраняются в:

```text
private/captures/<run-id>/<operationId>/request.json
private/captures/<run-id>/<operationId>/response.json
```

`private/.gitignore` игнорирует всё, кроме собственного `.gitignore` и `README.md`. CI отдельно проверяет, что capture-файлы не tracked.

Инварианты capture:

- сырой body существует только в памяти;
- raw capture mode отсутствует;
- auth request body не записывается никогда;
- `Authorization`, cookies, API keys, tokens и полные secret-bearing URL запрещены;
- сохраняются только allowlisted headers;
- binary bodies не сохраняются;
- UUID псевдонимизируются с сохранением связности внутри run;
- email, телефон, JWT, bearer-значения и известные секреты удаляются;
- свободные пользовательские строки редактируются;
- структура, типы и значимые enum сохраняются;
- перед записью выполняется финальный secret/PII scan;
- файл создаётся атомарно с правами `0600` только после успешного scan.

Минимальные metadata: `operationId`, HTTP method, обезличенный path, status, duration и run ID. Capture реализуется transport adapter тестовой инфраструктуры, а не изменением generated-клиента.

## 17. Секреты и локальная конфигурация

В Git разрешены только шаблоны без значений:

```text
.env.example
config/live-profile.example.toml
```

Реальные значения находятся в переменных окружения или игнорируемых `.env.local`, `private/` и `.state/`. Access token хранится только в памяти процесса и не кэшируется в файлах.

Перед commit/publish выполняются:

1. pinned secret scanner по tracked-дереву;
2. scan staged diff и запрещённых путей;
3. поиск точных загруженных секретов во всех планируемых артефактах без вывода самих значений.

Найденный секрет блокирует публикацию. Если секрет уже попал в remote, первым действием является его ротация; очистка Git-истории не считается заменой ротации.

## 18. Публикация

`sync` и `verify` никогда не создают commit. Публикация выполняется отдельно:

```bash
uv run python -m tools.openapi_pipeline publish \
  --version 0.1.0 \
  --push
```

`publish`:

1. проверяет отсутствие посторонних изменений в worktree;
2. повторяет offline `verify`;
3. проверяет успешную live-smoke receipt для текущих effective-schema и generated-code hashes;
4. проверяет отсутствие `429`, открытого circuit breaker и незавершённых mutation journals;
5. повторяет secret scan;
6. показывает diff summary;
7. добавляет только allowlisted pipeline-файлы;
8. создаёт один commit;
9. по явным параметрам создаёт tag и пушит текущую ветку.

Запрещены `git add -A`, force push и неявная публикация в основную ветку. Прямой push в `main` можно отдельно разрешить в локальной конфигурации, но он выключен по умолчанию.

Рекомендуемое сообщение:

```text
chore(sdk): sync iiko OpenAPI 2026-07-16
```

Версионирование следует SemVer:

- patch — исправление без изменения публичного API;
- minor — новые операции и модели;
- major — удаление или переименование публичного API.

## 19. CI

CI не получает live credentials и выполняет только:

- `verify`;
- воспроизводимую генерацию;
- package build/install;
- offline-тесты;
- secret scanning;
- проверку игнорируемых приватных путей.

Периодическая задача может скачать upstream и сообщить об изменении schema hash. Она не запускает live-тесты, не выполняет write-операции и не публикует новую версию автоматически.

## 20. Использование из Iikocloud-manager

Первый способ распространения — Git tag:

```toml
iikocloud-py-sdk = { git = "ssh://git@github.com/UserVanya/Iikocloud-py-sdk.git", tag = "v0.1.0" }
```

Во время совместной разработки используется path/editable dependency. Manager закрепляет tag или commit, а не плавающую ветку. Это исключает неожиданное изменение generated API после очередного upstream sync.

Различия авторизации между iiko Server и iiko Cloud реализуются в будущем manager-слое. SDK предоставляет сгенерированный auth endpoint и возможность передать полученный bearer token, но не копирует manager lifecycle в generated-код.

## 21. Повседневный сценарий

```bash
# Скачать схему, применить corrections и пересобрать SDK.
uv run python -m tools.openapi_pipeline sync

# Проверить воспроизводимость, тесты и пакет offline.
uv run python -m tools.openapi_pipeline verify

# Выполнить минимальный последовательный live smoke.
uv run pytest -m live_read_smoke -n0 --live-profile test-server

# После просмотра diff создать commit и push.
uv run python -m tools.openapi_pipeline publish --version 0.1.0 --push
```

Live write и HTTP capture запускаются отдельными, намеренно длинными командами. Они не являются частью обычного обновления.

## 22. Обработка отказов

| Событие | Обязательная реакция |
|---|---|
| Upstream недоступен или вернул не-JSON | Не менять snapshot и generated-код |
| Overlay guard не совпал | Остановить `sync`, пометить patch stale |
| Новый endpoint без `operationId` | Остановить генерацию до ручного naming review |
| Невалидная effective schema | Не запускать codegen |
| Ошибка генерации или package tests | Не продвигать staging в рабочее дерево |
| `429` | Остановить весь live-run, открыть circuit, запретить retry |
| Cleanup не завершён | Провалить run, сохранить mutation journal, запретить publish |
| Secret scanner нашёл совпадение | Не создавать commit |
| Посторонний dirty worktree | Не stage и не публиковать изменения |

## 23. Критерии приёмки первой итерации

Реализация считается готовой, когда:

1. `sync` из чистого checkout строит effective schema из точного upstream snapshot и correction layer.
2. Повторный `sync` с теми же входами не меняет файлы.
3. Изменённый upstream-фрагмент делает соответствующий overlay stale вместо молчаливого применения.
4. Effective schema проходит строгую validation без `--skip-validate-spec`.
5. Все операции имеют закреплённые уникальные `operationId`.
6. Известные menu `oneOf` не теряют ветки и покрыты contract-тестами.
7. Generated-код можно полностью удалить и воспроизвести из committed входов.
8. Wheel собирается, устанавливается в чистое окружение и импортируется.
9. Обычный `pytest` не выполняет сетевые или write-вызовы.
10. Неизвестная live-операция и параллельный live-запуск блокируются.
11. Синтетический `429` прекращает suite без retry и открывает circuit breaker.
12. Write-тест нельзя запустить без всех флагов, allowlist и rate plan.
13. Прерывание write-теста оставляет достаточный журнал для `cleanup-orphans`.
14. Capture никогда не пишет auth body, bearer token или известный секрет.
15. Попытка stage приватного файла или тестового секрета блокирует publish.
16. Успешный release устанавливается в отдельный проект по Git tag.

## 24. Осознанные компромиссы

- Явные overlays и registries требуют сопровождения, зато upstream-изменения не проходят незаметно.
- Большие интервалы и последовательные live-тесты делают suite медленным, зато снижают риск блокировки API login.
- Отсутствие retries может уменьшить удобство низкоуровневого SDK, но не скрывает опасные повторные запросы. Retry policy остаётся ответственностью manager.
- Ручной live gate замедляет публикацию, но CI не расходует лимиты и не хранит критичные credentials.
- Git tags достаточно для первого потребителя; PyPI добавляется только при реальной необходимости.

## 25. Что пересмотреть при росте

После стабилизации первой версии можно отдельно рассмотреть:

- публикацию signed artifacts в PyPI;
- централизованный rate-limit coordinator для нескольких машин;
- защищённый self-hosted runner для редких live smoke;
- upstream issue tracking и автоматическое закрытие исправлений после починки схемы iiko;
- миграцию `Iikocloud-manager` на доменные mixins и общий auth/rate-limit lifecycle.

Эти расширения не должны усложнять первую реализацию заранее.
